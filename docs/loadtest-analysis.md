## Analysis

Hand-written; the tables above are generated by `python -m st_inference.loadtest`.
Hardware: GTX 1650 (4 GB), `birefnet_lite` fp32 (fp16 is NaN on this chip — ADR-008), one worker.

### What the run found, and what I changed because of it

**1. fsync on every result cost 19% of the pipeline.** The stage profile measures 174 ms to store one
result with `fsync`, against 2 ms without — on a 913 ms pipeline. A result is a *derived* artifact: if a
power cut loses one, the job re-runs, and the API already answers 410 for a missing blob. Uploaded
originals still fsync, because those cannot be recomputed. Steady throughput went **0.264 → 0.333 img/s
(+26%)**.

**2. Worst-case recovery equals the visibility timeout.** In the first outage run, p99 end-to-end was
**302 s** — the 300 s timeout, exactly. A job claimed by the worker that then dies is invisible until the
timeout expires. With inference at ~0.6 s, minutes of invisibility buys nothing, so the default is now
**60 s**: outage p99 fell to **67 s**. If GPU inference ever gets slower than ~20 s per image, raise it again.

**3. No 5xx in any scenario, including a 15-second worker outage** with 22 jobs outstanding. Every
request returned 202 and every job completed after the worker came back. That is the brief's graceful
degradation requirement, demonstrated rather than asserted.

**4. Deduplication is worth roughly 100×.** A repeat upload of identical bytes completes in ~158 ms
against ~17.8 s cold (the cold figure is under burst load). Sellers re-send the same photo often, so
this is a real cost saving, not a benchmark artifact.

### Reading the throughput numbers

Three different numbers, all honest, measuring different things:

| | img/s | what it is |
|---|---|---|
| 1.10 | single-threaded pipeline (stage profile) | what one worker can do with a core to itself |
| 0.333 | steady, concurrency 4 | client and server sharing 6 cores on one laptop |
| 7.8 | `birefnet_lite` fp16 on a Tesla T4 (`eval/results.md`) | GPU-only, no HTTP, no encoding, no storage |

The gap between 7.8 and 1.10 is **not** the GPU. Inference is 64% of the pipeline here; PNG encoding is
14% and grows with image size. On a card where inference drops to ~130 ms, encoding and storage would
dominate — so before buying faster GPUs, do this:

1. **Encode WebP instead of PNG** (or PNG `compress_level=1`): 749 KB and 126 ms per cutout is the
   second-largest cost after inference.
2. **Move preprocessing to the GPU.** The benchmark already showed batching gains nothing because
   resizing is CPU-side and serial (`eval/analysis.md`).
3. **Scale by GPU, not by worker.** Workers are GPU-bound; a second worker on one card adds contention.

### What this run does not tell you

- **The queue was in-process (fakeredis)**, because neither Docker nor WSL could give me a real server
  on this machine. Semantics are identical (the same Redis-Streams code paths run), but there is no
  network hop, no AOF fsync and no cross-process contention. Re-run with `make up` for a true number.
- **Client and server shared one machine**, so the client's HTTP and JSON work competed with the
  worker's preprocessing. A separate load generator would raise throughput.
- **One worker, one small GPU.** Nothing here measures multi-GPU or multi-host behaviour.
- Latency percentiles in `steady` and `burst` are dominated by **queue wait**, not inference: 32 images
  behind one GPU means the last one waits for the other 31. That is why the bot replies "queued" and
  delivers asynchronously instead of making the seller hold.
